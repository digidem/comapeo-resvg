# AGENTS.md

Guidance for coding agents working in this repository. Read `README.md`
first for what the package does and how to build and test it.

## Layout

Tracked:

- `src/lib.rs` — the whole addon: input checks, the resvg call and PNG
  encoding, run as a napi `AsyncTask`. `Cargo.toml` turns resvg's default
  features off and napi's `dyn-symbols` off (see the comment there).
- `index.js`, `index.d.ts` — the JavaScript entry point, which loads the
  prebuild with node-gyp-build, and its types.
- `rust-toolchain.toml` — Rust version and the cross-compilation targets.
- `THIRD-PARTY-NOTICES.txt` — licenses of the crates compiled into the
  prebuilds, shipped in the package. Generated by `scripts/notices.sh`.
- `scripts/` — bash scripts that do all the work, plus the cargo-about
  config and template (`about.toml`, `about.hbs`) for `notices.sh`. Each
  script's header comment documents its usage and the reasons behind its
  flags; keep those comments current when changing a script.
- `test/test.js`, `test/bench.js`, `test/icons/`, `test/snapshots/` — the
  tests, the benchmarks, the 36 SVG fixtures and their reference PNGs.
- `test/resvg/` — a sample of resvg's own tests for filters, masks, clip
  paths, gradients and patterns, with resvg's reference PNGs. Copied
  unchanged from the resvg tag matching `Cargo.toml`; never regenerate them
  with this addon.
- `docs/performance.md` — threading, copies and benchmark numbers.
- `.github/workflows/ci.yml` — builds every prebuild, tests on desktop in
  Node and Electron and on the iOS simulator and Android emulators, and
  packs the package.
- `.github/workflows/release.yml` and `.changeset/` — releases with
  changesets. See Releasing below.

Generated and gitignored (safe to delete; the scripts recreate them):

- `target/` — cargo output.
- `prebuilds/<target>/comapeo-resvg.node` — output of `scripts/build.sh`.
- `vendor-runtime/` — nodejs-mobile release zips, unpacked
  (`fetch-runtime.sh`).
- `nodejs-project/` — the app payload the harness copies in
  (`assemble-project.sh`).
- `.harness/` — copy of the test harness, written by the run scripts.

## Pipeline

`fetch-runtime.sh` → `build.sh <target>` → `assemble-project.sh <target>` →
`run-ios.sh` / `run-android.sh`. `build.sh host` alone is enough for
`npm test` and `npm run bench` on the host.

`build.sh` ends with post-link checks (NodeMobile framework link and Mach-O
platform on iOS; `DT_NEEDED libnode.so` and 16 KB page alignment on
Android; exported `napi_register_module_v1`). A build that fails these is
not usable even if cargo succeeded.

Prebuild directories are named `<platform>-<arch>` as node-gyp-build
expects. The simulator reports `ios-arm64`, so `assemble-project.sh` puts
the `ios-arm64-simulator` build in `prebuilds/ios-arm64/`.

The run scripts need an iOS simulator or Android emulator and a
`nodejs-mobile-bare-prebuilds` checkout at `../` or `HARNESS_REPO`. The
harness runs `test.js` and prints a `__NODE_EXIT__:<code>` sentinel to the
app's stdout; `run-ios.sh` watches for it itself, and `run-android.sh`
leaves that to the harness's `run-test.sh`. Either way the exit code is the
test result. `BENCH=1` at assemble time puts `bench.js` in its place.

## Rules

- Don't set a global `RUSTFLAGS`. `build.sh` unsets it because it would
  replace the per-target `CARGO_TARGET_*_RUSTFLAGS`. Don't run `cargo build`
  for a mobile target by hand; the scripts set the link flags.
- Don't turn resvg's default features back on. Leaving out text and image
  support is deliberate: it keeps the addon to about 1–1.5 MB and stops an
  SVG from someone else reaching the filesystem. The `image_href_resolver`
  overrides in `src/lib.rs` are part of the same decision.
- Never hand-edit `test/snapshots/`. Regenerate with `npm run test:update`
  whenever the icons, `SIZES` in `test/test.js` or the resvg version change,
  and review the changed PNGs before committing. The same snapshots are used
  on every platform; a mismatch on device is a real rendering difference
  until proven otherwise.
- Builds use `--locked`. After changing `Cargo.toml`, update `Cargo.lock`,
  run `scripts/notices.sh` and commit all three. Never hand-edit
  `THIRD-PARTY-NOTICES.txt`; CI fails if it is out of date. A new crate
  under a license not in the `accepted` list in `scripts/about.toml` fails
  the script until the license is checked and added.
- The simulator and emulator CI jobs are skipped on pull requests to save
  macOS minutes; they run on pushes to `main` and manual dispatch.

## Bumping versions

Each version is set in more than one place; change all of them together:

- Rust and its targets: `rust-toolchain.toml`.
- resvg, napi, png: `Cargo.toml` and `Cargo.lock`.
- nodejs-mobile: `NODEJS_MOBILE_VERSION` in `scripts/fetch-runtime.sh`. The
  iOS 14 and Android API 24 minimums in `scripts/build.sh` come from it.
- Android NDK: the `ANDROID_NDK_HOME` default in `scripts/build.sh`, the two
  mentions in `.github/workflows/ci.yml`, and `README.md`.
- cargo-ndk, Node and Electron used by CI: `.github/workflows/ci.yml`.
- Adding or removing a prebuild target (not a version, but listed in as
  many places): `rust-toolchain.toml`, `scripts/build.sh`, the mobile job in
  `.github/workflows/ci.yml`, `scripts/check-prebuilds.sh`,
  `scripts/about.toml` and the README's prebuild table.
- cargo-about: `.github/workflows/ci.yml` and the header of
  `scripts/notices.sh`. If napi-rs changes its `LICENSE`, update the checksums
  in `scripts/about.toml`; `scripts/notices.sh` fails until then.
- Test harness: the `nodejs-mobile-bare-prebuilds` ref in both CI test jobs.
- resvg's tests in `test/resvg/`: copy the same files from
  `crates/resvg/tests/tests/` at the new resvg tag, and the tag in the
  README's license section.

## Releasing

Releases use [changesets](https://github.com/changesets/changesets). Every
pull request that changes what users get needs a changeset: run
`npx changeset` and commit the file it writes. Never run `changeset version`
by hand; the release workflow does it.

On each push to `main`, `release.yml` does one of two things:

- If changesets are pending, it opens or updates a "chore: version packages"
  pull request that bumps the version and writes `CHANGELOG.md`. Merging it
  is the sign-off for a release.
- If none are pending and the version in `package.json` isn't on npm, which
  is the case just after that pull request merges, it runs all of `ci.yml`,
  simulator and emulator tests included, packs the package with the
  prebuilds from that run (`scripts/check-prebuilds.sh` stops it if one is
  missing), publishes it to npm with trusted publishing (OIDC, no npm
  token), and tags and creates a GitHub release.

The version pull request is opened with the release-bot GitHub App's token
(`RELEASE_BOT_APP_ID` variable, `RELEASE_BOT_PRIVATE_KEY` secret), because a
pull request opened with the default token doesn't trigger CI.

## Conventions

- Commit titles follow Conventional Commits (`feat:`, `fix:`, `docs:`, …).
  The version is set by changesets, not by the commit type.
- Scripts are `bash` with `set -euo pipefail`, two-space indent, a header
  comment giving purpose and `Usage:`. Explain non-obvious flags with a
  short comment at the point of use, as the existing scripts do.
- The README is the user-facing document and should stay short. Rationale
  for individual build flags belongs in the script comments; measurements
  belong in `docs/`.
